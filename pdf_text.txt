ArcLab Engine Master Plan1. Executive Overview
ArcLab Engine is a custom scientific simulation engine and editor. The aim is not to build a game 
engine with physics attached. The aim is to build a physics-first experimentation environment where 
a user can construct a virtual experiment, run it, inspect the forces and fields involved, record the 
results, compare runs, and eventually let an AI assistant run parameter sweeps automatically.
The first version should be narrow but impressive: a 3D magnetic particle experiment where charged 
particles move through electric and magnetic fields, field lines are visible, real-time graphs update 
while the simulation runs, and users can save and reload the experiment. This demo is the seed of the 
whole platform because it proves rendering, physics, UI, data recording, graphing, experiment 
control, and scientific visualization in one integrated product.
Going full custom is the hard path. It means you build the window, renderer, editor, math layer, 
simulation loop, physics solvers, data recording, memory management, and eventually GPU compute 
yourself. The advantage is control. The disadvantage is time. You will move slower at the beginning 
than someone using Unity, Unreal, or Godot, but you will build a platform that can become specialized  
for scientific experiments instead of being trapped inside a game-engine design philosophy.
Core decision
Build the engine around experiments, not around levels, characters, and gameplay. Every 
subsystem should answer: does this help a user create, run, inspect, reproduce, or automate a 
physics experiment?
1.1 What this project is
A real-time 3D experiment editor.
A simulation engine with custom physics modules.
A scientific visualization platform for particles, fields, forces, heat, and motion.
A data recording and analysis tool that exports useful experiment results.
A future AI automation layer that can generate experiments, run sweeps, compare outputs, and 
suggest next tests.
1.2 What this project is not, at the start
It is not a full quantum mechanics platform on day one.
It is not a complete chemistry engine on day one.
It is not a nuclear-element discovery system on day one.
It is not a multiplayer cloud product on day one.
It is not a replacement for Ansys, COMSOL, CERN software, or national-lab simulation stacks at 
MVP stage.
1.3 The correct first demo
The first public demo should be called Magnetic Particle Confinement. It should show two 
electromagnetic coils, a charged particle emitter, visible magnetic field lines, blue/red particle trails, 
live graphs, and a control panel. The user should be able to change particle speed, charge, mass, field

2. Product Vision and Design Philosophy
2.1 The product vision
ArcLab should feel like a mixture of a 3D engine editor, a physics laboratory, an oscilloscope, and a 
research notebook. The user should not only see a cool simulation. The user should understand why 
the simulation behaves that way. This means the interface must expose variables, equations, force 
vectors, field directions, sensor readings, and experiment history.
The long-term vision is a virtual physics lab where a scientist, student, engineer, or company can test 
ideas before spending money on real hardware. A company could test thermal flow. A teacher could 
demonstrate electromagnetism. A researcher could run a fast approximation before moving to 
expensive high-fidelity software. Later, AI could explore large design spaces automatically.

4.2 OpenGL first vs Vulkan first
There are two valid routes. The practical route is OpenGL first, Vulkan later. The serious-engine route 
is Vulkan first. Vulkan first is painful but makes you learn the correct architecture earlier. OpenGL 
first gives you a faster first demo. If your motivation depends on seeing progress quickly, use OpenGL 
for the first 90 days and design the renderer abstraction so Vulkan can replace it later. If you are 
prepared for slow setup and debugging, start with Vulkan.

down too much. Otherwise, use Vulkan from day one and accept that the first month will feel 
brutal. The engine is long-term, so Vulkan is justified.
5. High-Level Architecture
ArcLab should be built as a core engine plus an editor application. The engine should not depend on 
the editor. The editor uses the engine. This separation matters because later you may want command-
line simulations, batch runs, server-side simulation jobs, or AI agents that run experiments without 
opening the full UI.

7.2 Fixed timestep
Use a fixed timestep for physics. Rendering can run at variable FPS, but physics should step at a stable  
interval such as 1/60 or 1/120 second. This prevents physics from changing when frame rate changes.
const double fixed_dt = 1.0 / 120.0;
accumulator += frame_dt;
while (accumulator >= fixed_dt) {
    physics_step(fixed_dt);
    accumulator -= fixed_dt;
}

8.2 Debug visualization is not optional

9. Physics Plan
9.1 First physics module: classical mechanics
Start with classical mechanics. This means mass, force, velocity, acceleration, gravity, drag, friction, 
and collisions. The reason is simple: every other module depends on reliable time integration and 
scene state management.
force_sum = gravity_force + external_forces + drag_force
acceleration = force_sum / mass
velocity += acceleration * dt

9.2 Collision system
Do collisions in stages. First, sphere-plane and sphere-sphere. Then AABB. Then broadphase spatial 
grids. Do not jump straight into complicated convex collision algorithms. The first target is stable and 
debuggable behavior.
Stage Collision types Purpose
Stage 1 Sphere-plane, sphere-sphere Make objects bounce and interact.
Stage 2 AABB-plane, AABB-AABB Support boxes and simple editor 
objects.
Stage 3 Spatial grid broadphase Avoid checking every object against 
every other object.
Stage 4 OBB and capsule Better shapes for tools and demos.
Stage 5 Convex collision Advanced only after basics are 
strong.
9.3 Particle physics
Particles are the visual identity of ArcLab. They let you show fields, trails, flows, and energy changes. 
Implement particles as a separate optimized system, not as thousands of heavy entities. Each particle 
should be simple and stored in contiguous arrays for cache efficiency.
struct Particle {
    Vec3 position;
    Vec3 velocity;
    Vec3 force;
    float mass;
    float charge;
    float temperature;
    float lifetime;
    uint32_t flags;
};
9.4 Electromagnetism MVP
Electromagnetism should be the first signature scientific module. You do not need a full Maxwell 
solver at the start. Begin with simplified electric and magnetic fields that apply force to charged 
particles. Use the Lorentz force equation as the basis.
F = q * (E + cross(v, B))
where:
q = particle charge
E = electric field vector
v = particle velocity
B = magnetic field vector

9.5 Heat module later
Heat simulation should come after particles and fields. Start with simple heat diffusion on a grid or 
between connected objects. Do not start with full fluid convection. A simple heat-map over a plane or 
object is enough for the first thermal demo.
9.6 Fluid module later
Fluids are difficult and can consume huge time. Delay serious fluids until the engine has stable 
rendering, particles, graphs, save/load, and profiling. For early visuals, use particle-flow 
approximations. Later explore grid-based fluid solvers, SPH, or simplified smoke simulation.
10. Memory and Storage Constraints
10.1 Why memory will become a major issue
The engine itself will not be huge. The problem is simulation data. If you store every particle, every 
frame, every field value, every sensor reading, and every graph sample without limits, your memory 
and disk usage will explode. Scientific tools must record data, but they must record intelligently.
10.2 Particle memory estimate
Particle count Approx memory at 64 bytes each Practical meaning
10,000 0.64 MB Easy. Good for first demos.
100,000 6.4 MB Still easy on CPU/GPU.
1,000,000 64 MB Possible, but update/render strategy 
matters.
10,000,000 640 MB Heavy. Requires GPU compute and 
careful buffers.
50,000,000 3.2 GB Research/benchmark territory, not 
early MVP.
10.3 History memory problem
Rewind and time history are dangerous. One million particles may be around 64 MB for one state. If 
you store 600 frames, that becomes about 38.4 GB. That is only particle state, not graphs, fields, logs, 
or rendering resources.
1,000,000 particles * 64 bytes = 64 MB per frame
64 MB * 600 saved frames = 38.4 GB
10.4 Memory rules
Do not store all particle data for every frame by default.
Use ring buffers for short-term rewind.
Use sparse snapshots for long-term history.
Let users choose what sensors record.

11. Performance Architecture
11.1 The biggest performance mistake
The biggest mistake is checking every particle or object against every other particle or object. This 
creates O(n^2) behavior. Ten thousand objects can become 100 million checks. One million objects is 
impossible with naive pairwise logic. You need spatial organization.
11.2 Broadphase approaches
Method Best for Difficulty
Uniform grid Particles and many similar objects. Low to medium. Start here.
Spatial hash Large sparse worlds. Medium. Good later.
Quadtree/octree Hierarchical space partitioning. Medium to high. Useful for uneven 
distributions.
BVH Meshes and ray queries. High. Use later for advanced 
collisions/rendering.

12.3 UI design rule
The UI should always make cause and effect visible. If the user changes field strength, the field lines, 
particle path, and graphs should make the effect obvious. The best demo is not just beautiful; it 
teaches the viewer what happened.

14. AI Assistant Roadmap
14.1 AI is not phase one
Do not build AI before the simulator works. AI needs tools to control. First build the engine, editor, 
sensors, graphs, save/load, and batch-run capability. Then AI can operate those systems.
14.2 What AI should do first
AI capability Description
Explain simulation Read current settings and explain what variables mean.
Suggest experiments Recommend changes to test a hypothesis.
Parameter sweep Run many experiments with different values.
Compare outputs Rank runs by a metric such as confinement time.
Generate report Summarize experiment setup, results, graphs, and next 
steps.
14.3 Tool interface for AI
Design internal commands before adding the AI model. The AI should call safe engine commands, not 
directly mutate memory. This keeps the system debuggable and safer.

22. Conclusion
Building a full custom engine is the hardest option, but it is aligned with the long-term vision. The 
correct strategy is to avoid pretending the first version will be a complete virtual universe. Instead, 
build a tight custom engine foundation, prove it with one strong experiment, and then grow the 
platform module by module.
The desktop should be the main development machine. Your hardware is enough for the first serious 
year if you manage memory carefully and avoid trying to simulate huge systems too early. The first 
major bottleneck will not be hardware. It will be engine architecture, math correctness, physics 
stability, debugging discipline, and scope control.
The right first mission is clear: build ArcLab Engine until it can create, run, visualize, record, save, 
and export a magnetic particle experiment. Once that exists, you have the foundation for everything 
else.
